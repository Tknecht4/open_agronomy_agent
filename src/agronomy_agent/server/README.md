# Server and service layer

## Purpose and status

`server/` composes the FastAPI application, application services, settings,
authentication/network boundaries, observability, and persistence. The React
cockpit is the supported interface. Runtime artifacts and request limiting are
local-only: filesystem and memory respectively. Ingest work is recorded in the
configured application database, which defaults to SQLite.

## Entry points

- `app.py:create_app` constructs the application and routes.
- `map_analysis_routes.py` registers the bounded synchronous `POST /api/geo/field-analysis` read endpoint; `services/field_map_analysis.py` validates geometry and computes geodesic measurements and clipped mapped coverage. It does not add a chat capability or persist field changes.
- `settings.py:build_settings` resolves environment and local defaults.
- `services/chat_service.py` coordinates the primary conversational path.
- `services/field_context_compiler.py` builds bounded field context.
- `services/tool_service.py`, `retrieval_service.py`, and `geospatial_service.py` expose capability domains.
- `services/answer_renderer.py` produces the user-facing answer/source structure.
- `storage/db.py` owns broad local SQLite persistence; `storage/runtime.py` exposes the schema-verified Postgres boundary.

## Service boundaries

Routes should authenticate and validate, call a service, map expected errors, and return a schema. Business logic belongs in `services/`; SQL and object bytes belong in `storage/`; core agronomic contracts belong above the server package. Avoid adding a second implementation of routing, tool registration, evidence authority, or answer validation in an endpoint.

Major endpoint domains include health/configuration, sessions and chat, field contexts and events, geometry/priors, retrieval and tools, attachments and image RAG, evaluation, data-source ingestion, exports, user/workspace administration, and observability. The exact OpenAPI document generated by the running application is authoritative for route shapes.

Both field-event append endpoints accept an optional `client_operation_id`
(UUID) on the SQLite runtime. Workspace authorization runs before receipt
lookup. Within one actor, a UUID binds the exact normalized request and field:
replay returns the original event with HTTP 201; changed contents or another
authorized field return HTTP 409 `field_event_operation_conflict`. Different
UUIDs and requests without a UUID retain distinct-save behavior. The event,
audit entry, and operation receipt commit in one SQLite transaction, survive
restart, and travel together in database backup/restore. Existing event hashes
and the field-event sync envelope are unchanged. Record-only sync does not
transfer retry receipts to another server database. The Postgres boundary
rejects requests that ask for this guarantee with HTTP 501
`field_event_idempotency_unavailable`; it does not silently ignore their UUIDs.

## Inputs and outputs

- Inputs: validated request schemas, authenticated actor/workspace context, `ServerSettings`, and configured stores/services.
- Outputs: versioned JSON or streaming events plus durable audit records where the operation mutates state.
- `GET /api/health` reports readiness metadata without local database paths and must return `status: ok` for the native quick-start health gate. It does not prove model generation, corpus sufficiency, or external-provider health.

## Invariants

- Local development authentication may bind only to loopback. Field-LAN mode requires TLS and one-time pairing. Hosted mode requires explicit identity configuration.
- Offline mode blocks public network adapters before a call.
- Workspace/user authority is checked before private state is read or mutated.
- Raw private records, credentials, and local absolute paths do not enter public exports.
- Retired Redis/S3 environment variables fail closed; no remote queue, rate-
  limit, or artifact-store selection remains.
- Trace and evidence identities survive rendering and persistence.

Localized agronomic concept corrections retain the original model draft and
explicit changed spans. The execution boundary accepts this provenance only
with a named supported defect, a nonempty edit record, a clean final assessment,
unchanged other prose and no editor/fallback claim. They remain bounded project
rules, not retrieved source evidence or a general scientific validation result.

A validated seed-survival clarification may execute two hypothetical arithmetic
scenarios while the plan remains `clarification_required`. The tool-execution
stage is `executed` with reason
`conditional_arithmetic_scenarios_no_selected_result`; this does not promote the
plan to ready or its evidence to ADEQUATE. The saved parent has no selected
value. Preview still performs no capability execution. Subsequent denominator
selection uses authorized prior user inputs and preserves the original turn.
The answer renderer skips Canadian source-gap prose only after exact whole
calculator-response replay; mixed requests, changed answers and other safety or
conflict disclosures retain their existing checks.

## Add or change an endpoint

1. Define or reuse a request/response schema in `schemas.py`.
2. Put domain logic in the owning service or core module.
3. Add the thinnest route in `create_app` and enforce auth/network/workspace rules.
4. Add service tests for success, validation error, unauthorized access, offline behavior, and persistence effects.
5. Update public docs only when the route is supported; label optional or untested deployments explicitly.

Adding an endpoint is not how a tool becomes available to chat. Register the capability and its executor/evidence adapter first; see [`../tools/README.md`](../tools/README.md).

## Configuration

Environment variables are normalized in `settings.py`. Prefer adding a typed
`ServerSettings` field with validation over reading environment variables
throughout services. Redis/S3 backend variables are deliberately retired and
rejected. Secrets remain environment- or provider-owned and must never enter
repository configuration.

These focused tests do not replace the full suite or a live UI/API exercise.

## Failure modes

Expected states include invalid request, unauthenticated/unauthorized, blocked
offline, model setup required, local storage unavailable, provider unavailable,
and validation failure. Fail closed when authority or egress is ambiguous;
return a useful status rather than fabricating a successful capability result.

## Conversation and runtime context

`POST /api/turn-readiness` previews the same turn payload through the canonical
tool/capability planners after authentication and field/session authorization.
It reads an optional existing session and creates no session, turn or operation
receipt. `requires_model` is false for validated unit conversion, supplied area
× mass-rate totals, including seed totals with a supplied rate, tank coverage,
fertilizer field totals, soil-water storage, bounded daily growing degree-day
inputs, the qualified supplied-model arithmetic forms, or the canonical missing-input
clarification. Unvalidated complete calculations remain
unknown. The response binds the request and current field/history state. Turn
submission reauthorizes, replans and rejects a stale binding, including after
waiting for the session guard; exact completed operation retries still replay.
Qualified calculator results and clarifications construct no generator. This preview is a readiness hint,
not agronomic authority or execution evidence.

`conversation_scope.py` binds a session to general questions, one saved field,
or one example. Both turn routes and session updates enforce the binding before
field authorization. A missing field snapshot is freshly loaded from authorized
storage. New turns use metadata-only session reads and a narrow, indexed latest-
turn query. Loading a saved conversation still returns its complete transcript.

`conversation_context.py` compiles a bounded, same-session active window into the
final model prompt. It preserves current input/evidence, drops oldest history
first, and refuses mandatory prompt overflow. Exact local tokenizer counts use
the actual chat template; HTTP/custom backends without a tokenizer receive a
labelled UTF-8 character estimate, which is not a hard provider token guarantee.
The configured budget includes the requested output allowance and is clamped to
a smaller declared native limit. Deterministic answers do not load a model for a
context indicator. Receipts live in `trace.metadata.context_budget`.

Before routing, `conversation_resolution.py` can resolve a numeric follow-up
such as “What about 200 instead?” from an immediately preceding complete typed
calculation request in the same authorized chat. It requires one unambiguous changed
numeric input and the same calculator operation. Assistant output supplies no
operand, explicit new requests remain authoritative, and ambiguous references
stay unresolved. The original user text is saved unchanged; the effective
question, source turn and policy are recorded in the trace and execution hashes.
The current tool recomputes the result, independent of the prior model's success.
The v5 calculation-reference policy also accepts an explicit whole-reply seed
denominator choice for seed-mass or seed-count calculations when that is the sole seed-calculator gap. A restated
survival percentage must exactly match the prior user input; “among” and “of”
identify the same denominator. Changed percentages and extra actions stay
authoritative as new requests. If conditional
survival then leaves only laboratory germination missing, one adjacent explicit
percentage reply can complete it. Both steps reconstruct only authorized user
requests, preserve all previous operands and the operation, and replan through
the current calculator. Extra actions, unrelated turns, failed/rejected history,
missing roots and other missing roles cannot supply this bounded seed chain.
Typed-tool ablations and baseline modes disable this interpretation. The legacy
stream bridge resolves references only from a contiguous suffix of completed
visible user/assistant pairs linked to saved turn IDs. A failed visible message
blocks the immediate follow-up; a later explicit completed calculation can
establish a fresh antecedent without deleting the failed message. Matching text
alone does not establish lineage.

Production turns for one in-process session are serialized from history read
through durable commit using the SQLite path and session identity; other sessions
can progress independently, including when separate store handles share that
path in one process. The optional
`client_operation_id` (UUID) on either `/api/sessions/{id}/turns` route binds a
submission to its exact request payload. A retry with the same ID and payload
returns the original completed turn, including its ID in turn metadata. A reused
ID with different payload returns `operation_conflict` (HTTP 409 for a saved
operation; an in-flight stream can emit the same error event). The operation
mapping and turn are committed atomically. A dropped stream is not evidence
that model work stopped; refresh the saved conversation before retrying. A
turn submission changes durable session context only for a newly completed
turn, so rejected or replayed operation IDs cannot overwrite context accepted
by a later turn. Turn binding and explicit session-context PATCH updates share
the same per-session guard and use the latest saved scope.
Hosted `/chat/stream` requests keep each thread's visible user/core/assistant
sequence ordered. If an ordinary request is cancelled while the process lives,
the app retains the accepted turn task until its assistant/trace write finishes;
process shutdown or crash does not guarantee that completion. The
ordering lock is process-local, consistent with the supported single-process
local runtime; cross-process deployment would need a database coordination
contract before claiming the same ordering behavior. The retained Postgres
runtime does not implement saved conversation persistence; those endpoints
return `conversation_storage_unavailable` (HTTP 501) rather than pretending
that the SQLite operation mapping applies there. SQLite backup/restore carries
the mapping with the database snapshot. There is no session-deletion API;
archiving leaves turns and operation receipts available.

Cache scope is an opaque hash of session identity plus draft/editor role. Cache
entries also bind model revision/snapshot and KV configuration, with aggregate
namespace/byte limits. Caching remains disabled in the active profile pending
matched real-model performance and quality measurements. Generation measurements
separate queueing, loading, tokenization, cache preparation and decode; HTTP rates
remain unavailable unless the backend supplies a meaningful measured boundary.


## Backup artifact references

`storage/backup.py` validates live attachment and export references against the
copied artifact tree before publishing a backup. Relocated restore validates the
original archive, rebases only store-owned absolute paths in its staged database,
and returns an `restore_transform` receipt with the transformed hash.
The restore journal binds that staged identity; source backup bytes are unchanged.
Relative export references remain relative. Missing files, unsafe paths and
recorded size/checksum mismatches stop publication. Deleted attachment tombstones
may have no file; legacy exports without recorded checksums receive presence checks.

Use an operator-controlled maintenance window with application writers stopped for
restore and reproducible backup. SQLite backup is an online database snapshot,
but it is not an atomic transaction with filesystem copies. These checks cover the
specified artifact root and optional knowledge-update tree, not the separately
configured imagery cache or arbitrary operator output directories.

### Actor-bound field-event operation protocol v2

`GET /api/demo/fields/{id}/events/operation-scope` uses the existing demo-field principal and write authorization. SQLite returns `protocol`, `actor_user_id`, `workspace_id`, `field_context_id`. It does not grant permission or change memberships. Unsupported receipt storage returns 501.

New clients include `client_operation_id`, `expected_actor_user_id`, `expected_workspace_id`, and `expected_operation_protocol` on either append route. Existing authorization runs before scope/receipt checks. A changed actor/workspace/protocol or incomplete expected scope returns 409 without append. Legacy clients may omit expected scope fields. Control fields do not enter immutable event data or request-content hashing. Successful operation-bearing appends include `operation` with the resolved scope, operation UUID and event ID; clients must verify that receipt. The actor/UUID SQLite ledger and event/audit append still commit atomically. Validation semantics must remain stable within the versioned protocol; bump its version if changing those semantics.

## Local request security

Every non-exempt request consumes the transport peer's in-memory rate budget
before route authentication. Supplied bearer, development-email, cookie and
forwarded headers do not establish this identity. At most 4,096 active windows
are retained; expired windows are removed and a full table rejects new peers
until a window expires. Active windows are never evicted to admit new callers.
This remains a single-process local control, not a distributed hosted limit.

Ordinary development authentication requires a single loopback Host and permits
only same-origin browser requests or explicitly configured loopback frontend
origins. The default Vite origins use port 5173; `run_cockpit.py --frontend-port`
passes the selected port. Direct CLI requests may omit Origin. Standalone
operators can set `AGRONOMY_AGENT_LOCAL_DEV_ORIGINS` to a comma-separated list of
loopback HTTP(S) origins. Forwarded transport headers are rejected in development
and desktop mode, and supported launchers disable proxy-header rewriting.
Desktop pairing retains its exact numeric HTTP origin. Every other pairing
exchange requires direct HTTPS at the API boundary, including custom launchers;
forwarding metadata is rejected even if a proxy has already rewritten the scheme. Rejection issues no session
cookie and leaves the one-time token available for a valid HTTPS request.
Field-LAN also requires development authentication disabled.

## Farms and field summaries

`farm_routes.py` and the local `farm_store` own farm membership, explicit seasons,
revision preconditions and grouped record writes. `field_import_routes.py` owns
bounded retained boundary previews and atomic idempotent commits. Existing field
IDs and histories are preserved; older undated crops are not assigned a year.
`field_context_store` and `field_enrichment` retain per-source status, scope,
freshness and receipts. `farm_summary` is read-only and makes no provider calls.
These new persistence capabilities currently require the migrated SQLite runtime;
other backends fail explicitly rather than pretending persistence succeeded.

`imagery_job_routes.py` owns bounded durable processing requests, cancellation,
restart interruption, authorized historical previews and record references.
`imagery_service` admits HLS and Sentinel-2 with independent validators and
read-back verification. Display overlays use a separate worker reprojection.
No browser supplies a worker path, arbitrary asset URL or execution environment.

Season records retain structured crop entries and an explicit single/intercrop/sequence/separate-areas system. Legacy single-crop rows are projected without changing their crop year; edits use the existing revision precondition. The trusted question compiler carries the saved structure and does not infer per-crop acreage or dates. Canadian dossier crop-cover refresh opts into `year: latest`, with a catalog response receipt; direct tool calls retain their pinned default or explicit year.

Seedling loss is not automatically the complement of overall emergence.
The two-scenario clarification requires directly supplied survival; mortality
inputs do not gain that path. A stage-specific seedling loss needs actual
overall emergence or an explicit loss definition among germinated seeds. The
parser and short follow-up resolver do not turn its complement into a supplied
overall survival fact. Explicit post-germination mortality remains supported.


### Timeline record bundles

The main timeline form posts `/api/fields/{field_id}/records` through
`farm_routes.py::RecordBundle` and `storage/field_record_store.py::append_bundle`.
This is separate from the single-event FieldSyncPanel protocol described above.
The local SQLite bundle transaction binds `(field_id, operation_id)` to the
normalized event payload digest in `field_record_operations`; exact retries
return the original events with `already_saved`, and changed payloads conflict.
Pydantic validation rejects a first invalid request before append with HTTP 422;
store validation conflicts return HTTP 409. A later rejection following an
unknown outcome does not prove the earlier attempt failed. Backups must include
the operation ledger, not just the event rows.

`RecordEntryDialog` captures its event JSON and operation UUID before dispatch,
locks edits during unknown outcomes, and checks returned IDs, field and submitted
content before clearing storage. It uses field/season/correction draft slots and
expected-version checks, rather than the separate sync client's actor partitions
and native Web Locks. `FarmRecords` offers recovery on a superseded original
when that correction slot remains unconfirmed. Neither client may interpret an
unknown observation date as a measured date or erase the immutable original.

## Selected satellite analysis in a question

The agronomic turn request accepts one optional `imagery_job_id` UUID. The
composer sends it separately from the question text, and the selection is
local to that draft. Asking reads an existing result. Saving an analysis
reference to field records remains an explicit action.

Readiness and submission authorize the saved field before resolving the ID.
A missing or other-field job returns 404. An incomplete or unverifiable job
returns 409. The server checks the job result against the verified private
chip, including the original geometry and request identity. Resolution uses
only local reads and does not launch a worker. A historical boundary remains
eligible by explicit selection and is labelled historical. The field season
identifies the conversation, while acquisition time identifies the image.

The field context compiler carries the result hash, source and acquisition,
grid resolution, original geometry status, support area, QA-clear area and
per-index valid area and mean. Zero valid index area has an absent mean.
The draft, verifier and evidence card use the same bounded projection.
Its authority is a processed spectral observation of eligible pixels.
It supplies no comparison baseline, diagnosis or action authority.

The readiness binding covers the selected result and the current field
snapshot. Submission revalidates both under the session guard. Completed
operation retries return the persisted turn. Full and answer-only agronomic
replay reauthorize and resolve the same result identity. Selections do not
become defaults for later questions in the conversation.
