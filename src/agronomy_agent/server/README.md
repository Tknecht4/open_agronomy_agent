# Server and service layer

## Purpose and status

`server/` composes the FastAPI application, application services, settings, authentication/network boundaries, queues, observability, and persistence. The React cockpit is the supported interface. Local SQLite operation is exercised; hosted Postgres and external infrastructure paths must be treated according to their explicit readiness checks, not assumed from the presence of code.

## Entry points

- `app.py:create_app` constructs the application and routes.
- `settings.py:build_settings` resolves environment and local defaults.
- `services/chat_service.py` coordinates the primary conversational path.
- `services/field_context_compiler.py` builds bounded field context.
- `services/tool_service.py`, `retrieval_service.py`, and `geospatial_service.py` expose capability domains.
- `services/answer_renderer.py` produces the user-facing answer/source structure.
- `storage/db.py` owns broad local SQLite persistence; `storage/runtime.py` exposes the schema-verified Postgres boundary.
- `worker.py` is the queue worker entry point.

## Service boundaries

Routes should authenticate and validate, call a service, map expected errors, and return a schema. Business logic belongs in `services/`; SQL and object bytes belong in `storage/`; core agronomic contracts belong above the server package. Avoid adding a second implementation of routing, tool registration, evidence authority, or answer validation in an endpoint.

Major endpoint domains include health/configuration, sessions and chat, field contexts and events, geometry/priors, retrieval and tools, attachments and image RAG, evaluation, data-source ingestion, exports, user/workspace administration, and observability. The exact OpenAPI document generated by the running application is authoritative for route shapes.

## Inputs and outputs

- Inputs: validated request schemas, authenticated actor/workspace context, `ServerSettings`, and configured stores/services.
- Outputs: versioned JSON or streaming events plus durable audit records where the operation mutates state.
- `GET /api/health` reports application configuration and must return `status: ok` for the native quick-start health gate. It does not prove model generation, corpus sufficiency, or external-provider health.

## Invariants

- Local development authentication may bind only to loopback. Field-LAN mode requires TLS and one-time pairing. Hosted mode requires explicit identity configuration.
- Offline mode blocks public network adapters before a call.
- Workspace/user authority is checked before private state is read or mutated.
- Raw private records, credentials, and local absolute paths do not enter public exports.
- Route handlers do not silently fall back from a configured hosted store to SQLite.
- Trace and evidence identities survive rendering and persistence.

## Add or change an endpoint

1. Define or reuse a request/response schema in `schemas.py`.
2. Put domain logic in the owning service or core module.
3. Add the thinnest route in `create_app` and enforce auth/network/workspace rules.
4. Add service tests for success, validation error, unauthorized access, offline behavior, and persistence effects.
5. Update public docs only when the route is supported; label optional or untested deployments explicitly.

Adding an endpoint is not how a tool becomes available to chat. Register the capability and its executor/evidence adapter first; see [`../tools/README.md`](../tools/README.md).

## Configuration

Environment variables are normalized in `settings.py`. Prefer adding a typed `ServerSettings` field with validation over reading environment variables throughout services. Secrets remain environment- or provider-owned and must never enter repository configuration.

## Validation

```bash
PYTHONPATH=src .venv/bin/python -m pytest -q \
  tests/test_chat_service_field_context.py \
  tests/test_field_events.py \
  tests/test_public_tool_adapters.py
curl --fail --silent http://127.0.0.1:8000/api/health | python -m json.tool
```

These focused tests do not replace the full suite or a live UI/API exercise.

## Failure modes

Expected states include invalid request, unauthenticated/unauthorized, blocked offline, model setup required, storage unavailable, queue unavailable, provider unavailable, and validation failure. Fail closed when authority or egress is ambiguous; return a useful status rather than fabricating a successful capability result.
